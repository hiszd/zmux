# Server-owned ephemeral sessions and workspaces

Accepted: zmux will use a background server as the authority for sequentially numbered Sessions, Workspaces, Tabs, PTYs, and terminal state, with multiple TUI Clients communicating through local IPC. Sessions are automatically assigned sequential numbers rather than user-defined names; launching without a target creates a new Session, while specifying an existing Session Number attaches to it. A Session contains one or more Workspaces; a Workspace contains Tabs and supplies the starting working directory for new Tabs, while each running Tab shell may change its own directory without changing the Workspace directory. Workspace directory changes occur through Workspace UI. A Workspace may have an explicit name; otherwise its name follows the working directory's basename. Creating a Workspace starts one Tab in its chosen directory and makes that Workspace active. Active Workspace and active Tab selections belong to Session state and are shared by all attached Clients; a Session retains its active Workspace, and each Workspace retains its active Tab while detached or switched away from. Each Client owns its configurable UI Element presentation and focus state; UI content is not Server state. Detaching closes only a Client; stopping the Server destroys all Sessions, and Sessions do not survive a server restart. Closing a Workspace's last Tab closes the Workspace; closing a Session's last Workspace closes the Session; the Server exits when its last Session is destroyed. Unix-like systems use a default and optional named socket under `$XDG_RUNTIME_DIR`, falling back to a private per-user runtime directory with a warning when it is unavailable; Windows uses a user-scoped named pipe through the same transport abstraction. This follows tmux's detach/reattach lifecycle while keeping restart recovery out of scope.
